# NetGuardian Security Detection & Confidence Scoring Methodology

## 1. Overview & Architecture

NetGuardian employs a hybrid, multi-layered defensive security detection architecture designed for real-time network digital twins:
- **Layer 1: Deterministic Rule Detection Engine** — Fast, low-latency stateful rule evaluation based on network invariants, access control boundaries, sliding window thresholds, and inventory tracking.
- **Layer 2: Unsupervised Machine Learning (Isolation Forest)** — Multivariate statistical anomaly detector evaluating multi-dimensional flow metrics against a continuously learned normal traffic baseline.

Every security event and alert generated by NetGuardian includes an explicit **Confidence Score** ($0.00$ to $1.00$ or categorical `High` / `Medium` / `Low`) to indicate detection certainty, reduce alert fatigue, and guide automated containment decisions in the Digital Twin.

---

## 2. Layer 1: Rule Engine Confidence Scoring

In the deterministic rule layer, confidence values represent the mathematical certainty that a detected pattern violates an explicit network security policy or statistical threshold, adjusted for source credibility and persistence.

### 2.1 Base Rule Confidence Values

| Rule Identifier | Threat Category | Base Confidence | Deterministic Logic & Rational |
| :--- | :--- | :---: | :--- |
| **RULE-01** | `UNKNOWN_DEVICE` | **0.95** (95%) | Exact cryptographic/network inventory lookup failure. An IP/MAC actively transmitting packets that has no entry in the authenticated device inventory represents a definitive rogue connection. |
| **RULE-02** | `PORT_SCAN` | **0.92** (92%) | Time-windowed distinct destination port count: $\ge \text{threshold}$ (default: 15 unique ports in 60s). High confidence due to distinct destination entropy. |
| **RULE-03** | `TRAFFIC_ANOMALY` | **0.88 - 0.91** (88-91%) | Flow volume or byte rate exceeding baseline multiplier (default: $3.0\times$ baseline or $\ge 500\,\text{KB}$ in single tick). Scaled by volumetric ratio. |
| **RULE-04** | `SUSPICIOUS_OUTBOUND` | **0.90** (90%) | Flow destined for known malicious or prohibited remote ports (e.g., Metasploit C2 `4444`, IRC botnet `6667`, Elite `31337`, or legacy cleartext services `21`, `23`). |
| **RULE-05** | `CRITICAL_ASSET_ACCESS` | **0.96** (96%) | Strict topological segmentation breach: Any direct connection to the protected Database (`192.168.1.21:5432`) originating from any host other than the designated Application Server (`192.168.1.20`). |
| **RULE-06** | `FAILED_AUTH` | **0.94** (94%) | Rapid authentication failures: $\ge 5$ consecutive invalid credential attempts within a 30-second sliding window against network assets or management interfaces. |
| **RULE-07** | `COMPROMISED_HOST` | **0.96** (96%) | Composite correlation scenario combining lateral movement, port scanning, and outbound command execution from a single endpoint. |

### 2.2 Dynamic Confidence Modifiers

When an alert is updated or evaluated across consecutive ticks, the base confidence is adjusted dynamically:

1. **Persistence & Recurrence ($C_{persist}$):**
   When the same source device repeats an anomalous behavior across multiple ticks while an alert remains open (`NEW` or `INVESTIGATING`), confidence is boosted:
   $$\text{Confidence} = \min\left(0.99, \text{Base} + 0.02 \times \log_2(\text{occurrence\_count})\right)$$
   This ensures persistent threats converge toward near-certainty ($99\%$) without producing redundant alert rows.

2. **Source Device Trust Factor ($C_{trust}$):**
   - Untrusted / Unregistered source (`trust_score` $\le 30$): $+0.03$ confidence bonus (higher probability that unusual behavior is genuinely malicious).
   - High-trust infrastructure (`trust_score` $\ge 85$, e.g., Core Router, Switch): $-0.05$ modifier triggering secondary verification before automated isolation.

## 3. Layer 2: Machine Learning Anomaly Confidence

The unsupervised ML engine evaluates high-dimensional flow feature vectors:
$$\mathbf{x} = [\text{packet\_count}, \text{bytes}, \text{duration}, \text{bytes\_per\_second}, \text{is\_common\_port}, \dots]$$

### 3.1 Isolation Forest Anomaly Metric

Isolation Forest isolates observations by randomly selecting a feature and splitting value:
$$s(x, n) = 2^{-\frac{\mathbb{E}(h(x))}{c(n)}}$$
where $h(x)$ is the path length of point $x$ in a tree of $n$ instances, and $c(n)$ is the average path length of unsuccessful searches in a Binary Search Tree (BST).

- When $\mathbb{E}(h(x)) \to 0 \implies s \to 1$ (highly anomalous; isolated rapidly with few splits).
- When $\mathbb{E}(h(x)) \to n - 1 \implies s \to 0$ (normal central distribution).

### 3.2 Categorical Confidence Mapping

The continuous anomaly score $s \in [0.0, 1.0]$ is translated into operator-friendly confidence tiers:

| Anomaly Score Range | Categorical Confidence | Operational Interpretation |
| :--- | :--- | :--- |
| **Score $\ge 0.75$** | **High** | Strong ensemble consensus ($> 90\%$ of trees isolated the sample at shallow depth). High statistical significance outside the 95% confidence hyper-ellipsoid. |
| **$0.55 \le \text{Score} < 0.75$** | **Medium** | Moderately deviated flow. Warranting analyst review or correlation with Layer 1 rule events. |
| **Score $< 0.55$** | **Low** | Marginal deviation within normal traffic variance bounds. Filtered from high-priority alert queues. |

## 4. De-duplication and Alert Correlation

To maintain a clean security operations posture and prevent alert flooding:
- Open alerts are keyed on `(event_type, source_device)`.
- If an alert of identical type and source is currently active, the detection pipeline increments `occurrence_count`, updates `last_seen`, appends recurrence metadata to the alert description, and recalculates confidence without creating redundant database records.
- In the Digital Twin, confirmed alerts dynamically update device `risk_score` and degrade `trust_score`, enabling automated what-if blast radius analysis and isolation simulation.

## 5. Explainable Device Risk & Trust Derivation Methodology

NetGuardian provides 100% explainable, transparent device risk evaluation based on strict mathematical separation of concerns:
- **Zero baseline risk**: An online device with no security findings has $\text{Risk Score} = 0.0$, regardless of its asset criticality. Criticality determines *how much an event matters* when a threat occurs, rather than generating phantom risk on benign nodes.
- **Zero double counting**: One security event adds points exactly once. Secondary status flags (such as marking a device `SUSPICIOUS`) do not add redundant penalty points for the same underlying event.
- **Zero circular dependency**: Risk is calculated strictly from active event findings and physical device state. Risk **never** reads or depends on trust score. Trust is derived as a strict one-way function: $\text{Trust} = \text{Base Trust} - \text{Risk Score}$. Recomputing risk and trust $N$ times is provably idempotent.

### 5.1 Distinct Risk Causes & Point Formulation

$$\text{Risk}_{\text{raw}} = \sum_{F \in \text{Factors}} \text{Impact}(F)$$

Every factor in the factor list originates from an independent, mutually exclusive cause:

1. **Cause 1: Active Threat Event Findings:**
   - Evaluated for each unresolved alert (`NEW`, `INVESTIGATING`) targeting or originating from the device:
     $$\text{Impact} = \text{Base Threat Points} \times M_{\text{crit}}$$
     - Base Points: `PORT_SCAN` ($25.0$), `COMPROMISED_HOST` ($35.0$), `CRITICAL_ASSET_ACCESS` ($30.0$), `SUSPICIOUS_OUTBOUND` ($25.0$), `FAILED_AUTH` ($20.0$), `UNKNOWN_DEVICE` ($20.0$), `TRAFFIC_ANOMALY` ($15.0$), `AI_ANOMALY` ($20.0$).
     - Criticality Multiplier ($M_{\text{crit}}$): `CRITICAL` ($1.4\times$), `HIGH` ($1.2\times$), `MEDIUM` ($1.0\times$), `LOW` ($0.8\times$).
2. **Cause 2: Availability / Offline Failure:**
   - $+10.0$ pts if node status is `OFFLINE` (connectivity health probe failure).
3. **Cause 3: Identity / Unregistered Origin Deficit:**
   - $+20.0$ pts if node origin is `UNTRUSTED` (unregistered device communicating on network).
4. **Cause 4: Remediation / Simulated Isolation Containment Credit:**
   - $-20.0$ pts containment credit if `is_isolated` is true (attack propagation severed in Digital Twin).

**Upper Normalization Cap**:
$$\text{Risk Score} = \max\left(0.0, \min\left(100.0, \text{Risk}_{\text{raw}}\right)\right)$$
If $\text{Risk}_{\text{raw}} > 100.0$, an `Upper Risk Cap Normalization` factor with impact $(100.0 - \text{Risk}_{\text{raw}})$ is appended so that:
$$\sum_{F \in \text{Factors}} \text{Impact}(F) \equiv \text{Risk Score}$$

### 5.2 Trust Score Derivation (One-Way Non-Circular)

$$\text{Base Trust} = \begin{cases} 95.0 & \text{HIGH (Router, Switch, Core Server, Database)} \\ 80.0 & \text{MEDIUM (Workstations, Laptops, Printers)} \\ 50.0 & \text{LOW (Mobile phones, IoT Cameras)} \\ 20.0 & \text{UNTRUSTED (External WAN / Unregistered)} \end{cases}$$

$$\text{Trust Score} = \max\left(0.0, \min\left(100.0, \text{round}\left(\text{Base Trust} - \text{Risk Score}, 1\right)\right)\right)$$

Because Risk does not depend on Trust, computing $(\text{Risk}, \text{Trust})$ repeatedly yields identical values.

## 6. NetGuardian Network Health Score & Clamping Methodology

The network health score is evaluated across 5 capped penalty categories and strictly clamped to $[0.0, 100.0]$:

$$\text{Health Score} = \max\left(0.0, \min\left(100.0, 100.0 - P_{\text{total}}\right)\right)$$

where:
$$P_{\text{total}} = P_{\text{threats}} + P_{\text{suspicious}} + P_{\text{high\_risk}} + P_{\text{anomalies}} + P_{\text{offline}}$$

### 6.1 Penalty Categories & Strict Caps

| Category | Description & Weights | Maximum Cap |
| :--- | :--- | :---: |
| **Active Threats ($P_{\text{threats}}$)** | Unresolved alerts (`NEW`, `INVESTIGATING`): Critical ($15.0$), High ($10.0$), Medium ($5.0$), Low ($2.0$) | **$35.0$ pts** |
| **Suspicious Devices ($P_{\text{suspicious}}$)** | Compromised hosts ($15.0$ each), Suspicious hosts ($10.0$ each) | **$25.0$ pts** |
| **High-Risk Nodes ($P_{\text{high\_risk}}$)** | Devices with $\text{Risk Score} \ge 70.0$ ($8.0$ each) | **$20.0$ pts** |
| **Traffic Anomalies ($P_{\text{anomalies}}$)** | Recent anomalous flow records ($2.5$ each) | **$15.0$ pts** |
| **Offline Devices ($P_{\text{offline}}$)** | Offline nodes: Critical ($10.0$), High ($6.0$), Medium/Low ($3.0$) | **$15.0$ pts** |

### 6.2 Clamping & Status Labels

- When extreme threats occur ($P_{\text{total}} > 100.0$), the score is clamped at $0.0$ (`CRITICAL`), and the UI explains: *"Health score is clamped at 0.0 because raw penalties totaled X pts, exceeding 100."*
- **$\ge 85.0$**: `HEALTHY` (Nominal operations, zero active high-severity threats)
- **$70.0 - 84.9$**: `NEEDS ATTENTION` (Minor abnormalities or low-severity alerts)
- **$50.0 - 69.9$**: `AT RISK` (Active port scans, multiple suspicious endpoints, or elevated anomaly counts)
- **$< 50.0$**: `CRITICAL` (Active compromise, critical asset breach, or widespread failure)

## 7. NetGuardian Simulated Path Risk & What-If Traversal Methodology

### 7.1 What-If Attack Graph Traversal Principles
The What-If Engine provides safe, non-destructive exploratory modeling answering: *"What systems could be impacted if this device is compromised?"*
1. **Safety Boundary**: Never attacks, probes, or modifies physical or production hardware. Traverses the in-memory Digital Twin graph strictly.
2. **Structural Topology Only**: Graph traversal operates exclusively on verified infrastructure links (`edge_type == "structural"`). Ephemeral application flows are excluded from topology reachability.
3. **Exclusion Rules**:
   - `Internet` WAN gateway node is excluded from lateral enterprise traversal.
   - Any node marked `OFFLINE` or `ISOLATED` is excluded as both a traversal hop and destination.
   - If the selected source node is offline or isolated, traversal returns 0 reachable systems without error.
4. **Critical Asset Prioritization**: Attack paths reaching high-criticality enterprise assets (`CRITICAL` Database) are prioritized as the primary exploratory attack vector.

### 7.2 NetGuardian Simulated Path Risk Formula
Simulated Path Risk assesses hypothetical blast-radius exposure on a strict 0 to 100 scale:

$$\text{Simulated Path Risk} = 0.30 \times R_{\text{source}} + 0.35 \times C_{\text{target}} + 0.15 \times H_{\text{proximity}} + 0.20 \times T_{\text{avg}}$$

where:

1. **Source Device Risk ($R_{\text{source}}$)**: Current calculated risk score of the compromised origin node ($0.0 - 100.0$).
2. **Target Criticality Value ($C_{\text{target}}$)**:
   $$C_{\text{target}} = \begin{cases} 95.0 & \text{CRITICAL (Crown-Jewel Database)} \\ 70.0 & \text{HIGH (Core Application Server, Router, Switch)} \\ 45.0 & \text{MEDIUM (Workstations, Laptops)} \\ 20.0 & \text{LOW (Printers, IoT Cameras, Mobile Phones)} \end{cases}$$
3. **Hop Proximity Factor ($H_{\text{proximity}}$)**:
   $$H_{\text{proximity}} = \max\left(0, 100 - 20 \times (\text{hops} - 1)\right)$$
   Direct 1-hop lateral neighbor receives 100.0 factor; 2 hops = 80.0; 3 hops = 60.0; 4 hops = 40.0; 5 hops = 20.0; $\ge 6$ hops = 0.0.
4. **Average Implicit Trust Along Path ($T_{\text{avg}}$)**:
   $$T_{\text{avg}} = \frac{1}{|P|} \sum_{v \in P} \text{trust\_score}(v)$$
   Arithmetic mean of trust scores across all nodes $v$ on traversal path $P$.

### 7.3 Risk Classification Tiers

| Path Risk Score | Level | Operational Interpretation |
|---|---|---|
| **$< 30.0$** | `LOW` | Minimal blast radius; isolated endpoints or low-criticality nodes. |
| **$30.0 - 54.9$** | `MEDIUM` | Lateral path into general subnet; standard segmentation controls apply. |
| **$55.0 - 79.9$** | `HIGH` | Path reaches core servers or critical assets within 2–3 hops. |
| **$\ge 80.0$** | `CRITICAL` | Severe proximity to Crown-Jewel Database from elevated-risk host. |

### 7.4 Simulated Isolation & Path Severance
1. **Link Severance**: Incident edges in the Digital Twin graph are deactivated (`active = False`), reducing reachable nodes from $N \to 0$ (100% path severance).
2. **Containment Credit**: Device receives a $-20.0\text{ pts}$ containment credit in its risk score breakdown.
3. **Event Lifecycle Update**: All open alerts and security events associated with the device automatically transition to `CONTAINED`.
4. **Traffic Silencing**: The synthetic traffic engine suppresses all flow synthesis originating from or destined to the isolated IP.
5. **Exact Action Feedback**:
   `"SIMULATED ACTION — [device] isolated. Potential attack path interrupted. No real network changes were performed."`
